# 数据质量与建模决策

## 数据概况

九个 Olist CSV 文件均已发现并成功导入 DuckDB。核心表规模如下：

| 表 | 记录数 |
|---|---:|
| 订单 | 99,441 |
| 订单明细 | 112,650 |
| 支付记录 | 103,886 |
| 评价记录 | 99,224 |
| 客户 | 99,441 |
| 商品 | 32,951 |
| 商家 | 3,095 |
| 地理位置 | 1,000,163 |

分析层保留 99,441 行订单和 112,650 行订单明细，与原始层一致。订单、客户、商品、
商家、支付和评价之间未发现无法匹配的外键记录。

## 主要质量问题

### 评价主键与多评价订单

- `review_id` 只有 98,410 个不同值，不能单独作为主键。
- `review_id + order_id` 在 99,224 条评价中保持唯一。
- 547 个订单存在多条评价，其中 202 个订单的评分发生变化。

建模采用 `review_id + order_id` 作为评价记录标识。连接订单宽表前，按
`review_answer_timestamp` 排序，保留每个订单最后提交的一条评价，同时保留
`review_count` 供质量分析。

### 缺失数据

- 订单实际送达时间缺失 2,965 条，主要与尚未送达、取消或不可用状态有关。
- 评价标题缺失 88.34%，评价正文缺失 58.73%。文本字段不能作为评价分析的必需条件。
- 610 个商品缺少品类及相关描述字段，占商品表 1.85%。品类分析将其标记为未知，不删除订单。
- 2 个商品缺少重量和尺寸字段。涉及物流体积或重量时单独排除并报告样本量。

### 支付对账

在同时存在商品明细和支付记录的 98,665 个订单中，98,278 个订单的支付金额与
商品金额加运费之间误差不超过 0.01，对账通过率为 99.61%。平均绝对差额为 0.03，
最大绝对差额为 182.81，总差额为 2,870.39。

因此：

- GMV 使用订单明细中的 `price` 求和，不用 `payment_value` 替代。
- 运费单独使用 `freight_value` 分析。
- `payment_value` 仅用于支付方式、分期和金额对账专题。
- 对账异常订单保留，后续作为数据质量案例分析。

### 时间范围

原始下单时间为 2016-09-04 至 2018-10-17。2016年仅有零散订单；2018年9月仅有1笔
有效订单，之后没有完整经营数据。

月度趋势、同比和品类增长分析使用 2017-01-01 至 2018-08-31 的完整月份。全量规模、
状态分布和数据质量统计仍使用全部记录。

## 基准指标

基于“已购买且状态不为 canceled 或 unavailable”的第一版有效订单口径：

| 指标 | 结果 |
|---|---:|
| 有效订单 | 98,207 |
| GMV | 13,494,400.74 |
| 客单价 | 137.41 |
| 有效用户 | 94,990 |
| 复购用户 | 2,888 |
| 复购率 | 3.04% |
| 最终评价平均分 | 4.086 |
| 延迟配送率 | 8.11% |

这些结果是后续分析的基准值，不直接作为最终业务结论。后续专题需明确时间范围、订单状态、
分析粒度和有效样本量。

## 下一步分析顺序

1. 月度 GMV、订单量和客单价趋势，识别增长阶段与异常月份。
2. 品类和地区增长贡献，解释经营变化来源。
3. 用户复购和 Cohort 分析，判断低复购率的结构性原因。
4. 配送延迟与评分关系，定位地区、品类和商家问题。
5. 在标准 SQL 稳定后构建电商语义层和 AI Copilot 评测集。
